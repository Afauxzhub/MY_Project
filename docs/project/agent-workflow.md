# Agent 开发工作流

这套流程服务于个人项目。目标是让每次工作都有明确结果，并让新任务、上下文压缩和换电脑后都能从仓库恢复状态。

## 1. 任务怎么分

一个任务对应一个能够独立验收的结果，例如“创建 Unity 工程并让现有包通过编译”。不要用“完成战斗系统”这类无法一次验收的范围。

- 同一个问题的实现、测试和修复留在同一任务中。
- 目标发生变化，或新工作可以独立交付时，创建新任务。
- 跨多次工作、涉及多个系统或需要实际运行验收时，建立任务卡。
- 小型文档修正或单点问题可以只占任务索引一行。

## 2. 总控任务与开发任务

保留一个项目总控任务，用于读取 `overview.md` 和 `tasks.md`、梳理需求、选择下一项工作和检查总体进度。总控任务不依赖聊天记忆维护状态。

具体开发按任务卡另开 Codex 任务。开发任务负责实现、验证、修复、更新自己的任务记录，并在结束时留下可供下一任务接管的说明。

建议同一时间只进行一个主要实现任务。确实独立的并行工作使用不同 Git worktree，且不能修改同一批文件。

## 3. 子代理怎么用

子代理用于边界清晰的临时工作，例如：

- 调查调用链或兼容性问题。
- 独立运行静态检查或审查变更。
- 分析一组失败日志或复现步骤。

子代理不长期拥有模块，也不维护自己的进度总表。主任务负责合并结论、验证最终结果并更新仓库记录。

## 4. 每个任务的生命周期

1. 读取 `AGENTS.md`、项目总览、任务索引和本任务卡。
2. 读取任务涉及的权威设计、架构或工具文档。
3. 确认依赖、范围、验收条件和运行验证边界。
4. 把状态改为 `In Progress`，记录开始日期。
5. 实现并运行与风险相称的检查。
6. 如果需要用户在 Unity 或 3ds Max 中操作，给出短小、可观察结果的验收步骤。
7. 记录验证结果、未解决问题、相关提交和下一项动作。
8. 达到全部验收条件后改为 `Done`；只缺实际运行验证时改为 `Awaiting Runtime Validation`。

## 5. 给 Agent 的任务输入

发起开发任务时，至少说明：

```text
目标：要得到什么可观察结果。
上下文：任务卡、相关设计和相关目录。
约束：必须遵守的兼容性、规则 ID 和禁止事项。
完成条件：哪些检查或实际行为通过才算完成。
交付：实现、验证、任务记录，以及未验证边界。
```

如果需求还比较模糊，先让总控任务把它整理成任务卡，再开始实现。

## 6. 设计、代码与测试的关系

- `[CONFIRMED]` 设计规则只能按对应维护流程修改。
- `[TUNING]` 数值通过灰盒证据调整，任务记录引用测试结果。
- `[OPEN]` 内容可以预留接口，不能由实现任务自行决定永久行为。
- 静态检查、Unity 编辑器验证、3ds Max 验证和游戏手感验证分别记录。
- 发现问题时先把复现条件和影响写入当前任务；不属于当前范围的问题再进入任务索引。

## 7. 会话结束时的交接格式

```text
已完成：
已验证：
尚未验证：
已知问题：
下一步：
相关任务/提交：
```

聊天可以被压缩或结束；仓库中的任务卡、设计文档、代码、提交和验证结果必须足以让下一次工作继续。
