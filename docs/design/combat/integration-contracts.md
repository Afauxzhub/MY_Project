# 战斗设计集成契约

| 字段 | 内容 |
| --- | --- |
| 文档版本 | 0.1.0 |
| 权威设计 | `player-combat-spec.md` |
| 用途 | 把玩家设计翻译为程序、动作、Boss与AI可以共同引用的接口 |

本文件只描述如何使用权威规范，不取代或复制完整玩法定义。如有冲突，以 `player-combat-spec.md` 为准。

## 1. 程序框架契约

### 1.1 顶层战斗状态

程序至少需要区分：

```text
OutOfCombat
NormalCombat
EnhancedCounterCombat
CombatSuspended
```

- `NormalCombat`维护黄色与蓝色。
- `EnhancedCounterCombat`锁定黄色，维护灰色与蓝色。
- `CombatSuspended`用于Boss阶段演出或玩家不可操作流程，冻结蓝色结算、灰色流失和相关战斗计时。
- 战斗结束时执行 `RES-BLUE-13`，而不是等待玩家站在原地观看蓝色缓慢结算。

### 1.2 资源事件与顺序

建议把结算实现为明确事件，而不是分散写在动作状态中：

```text
PendingResourceGenerated
PendingResourceSettled
PendingResourceLost
SpendableResourceConsumed
EnhancedStateEntered
EnhancedStateExited
GreyDrainRateChanged
CombatTimerSuspended
```

关键顺序：

1. 普攻命中先触发 `PendingResourceGenerated`，加入蓝色。
2. 看破成功先读取事件发生前已有蓝色，再执行结算。
3. 弹开输入先从黄色或灰色预付成本；成功后才结算已有蓝色。
4. 反击触发时结算此前已有蓝色；触发反击的当前攻击不得再产生蓝色。
5. 防御被命中时清空蓝色，再处理本次防御资源消耗。
6. 实际受击时清空蓝色、处理生命伤害，再根据伤害量增加灰色流速。
7. 进入强化状态时黄色转换为灰色，原有蓝色原样保留。
8. 灰色到零时先清空蓝色，再退出强化状态，黄色保持为零。

所有数值应数据驱动。帧窗口、资源量、流失速度和修复量不得硬编码为规范中的灰盒估值。

### 1.3 玩家动作状态

程序框架至少需要表达：

- 自由态。
- 普攻前摇、有效帧、后摇。
- 蓄力与蓄力释放。
- 普通闪避与看破窗口。
- 弹开窗口与持续防御。
- 反击自动躲避与反击攻击。
- 主动技能前摇、有效阶段与后摇。
- 奥义前摇、释放、主动取消和被打断。
- 受击僵直、可闪避脱离阶段与不可脱离阶段。
- 敌人破韧输出窗口。

取消优先级必须满足：

- 普攻后摇开始后允许闪避和防御。
- 闪避可用时间不得晚于弹开。
- 主动技能的连段取消时间晚于闪避与防御。
- 主动技能不能取消受击僵直。
- 反击是攻击判定触发的状态转换，不是独立输入技能。

### 1.4 数据标签

建议玩家和敌人招式数据至少提供以下标签或曲线：

- `CanTriggerCounter`
- `CounterWindow`
- `CanBeCountered`
- `CounterableImpactWindow`
- `CanBeRepelled`
- `CanBeBlocked`
- `CanBeEvaded`
- `NormalInsightWindow`
- `PerfectInsightWindow`
- `ContinuesComboAfterInsight`
- `EndsComboAfterRepel`
- `IsSpecialTelegraphedAttack`
- `LifeDamage`
- `StaggerDamage`
- `PendingResourceGain`
- `CancelToEvadeTime`
- `CancelToGuardTime`
- `CancelToSkillTime`

标签名称可以随实际代码风格调整，但表达能力不得缺失。

## 2. 动作需求契约

### 2.1 每个玩家动作需求必须包含

```text
动作名称/ID：
用途与对应规则ID：
输入与前置状态：
前摇：
有效攻击阶段：
后摇：
可闪避取消点：
可防御/弹开取消点：
可技能取消点：
反击窗口：
命中与失衡反馈：
位移或Root Motion：
镜头/停顿/时间缩放需求：
被打断与分支：
游戏事件或动画Notify：
仍属TUNING的内容：
```

### 2.2 动作制作原则

- 敌我危险动作必须有可读前摇，满足 `VISION-05`。
- 动画表现帧和最终玩法判定帧必须能够分离调整。
- 反击窗口需要附着于具体攻击动作，但最终触发还要检查敌人攻击的命中阶段。
- 反击演出结束后必须留出可顺畅回到L1压制的过渡，满足 `RES-GREY-14`。
- 看破需要支持保留连段段数与短Offset，不应被动作状态机自动重置为L1。
- 弹开成功与失败、持续防御命中、蓝色损失需要有明显不同的视听反馈。
- 灰色流速变化、蓝色结算和蓝色丢失不应只依赖UI数字，应有足够的角色或特效反馈。

## 3. Boss攻击与AI契约

### 3.1 每个Boss攻击必须声明

```text
招式名称/ID：
战斗目的：抢回合 / 连段延续 / 反制压制 / 位移追击 / 机制攻击
可见前摇与识别特征：
实际命中阶段：
是否可防御：
是否可弹开：
是否可普通看破：
是否触发完美看破：
是否可反击及有效阶段：
看破后连段是否继续：
弹开后连段是否结束：
命中后的受击等级：
生命伤害与失衡伤害：
AI使用条件与阶段权重：
针对玩家重复行为的合理变化：
引用的玩家规则ID：
```

### 3.2 Boss设计原则

- 一组Boss攻击不能全部由单一操作获得最高收益。
- 普通看破后的攻击动势应继续，使Offset保留成为即时决策而不是安全暂停。
- 弹开适合作为连段起手的终止方案，但其资源成本和可弹开范围需要控制，不能让玩家无脑打断全部Boss行为。
- 可反击攻击的命中阶段必须与动画接触相符，不能额外制造玩家不可见的双重窄窗。
- 特殊攻击与敌人弹开后的反制可以提供更宽的完美看破判定，但必须有一致、可学习的视觉语言。
- Boss破韧、转阶段和不可操作演出必须正确调用战斗暂停事件。
- AI可以根据距离、阶段和近期玩家行为改变招式权重，但不能读取输入后无前摇地硬性反制。

## 4. 测试契约

第一版灰盒至少记录：

- 从零到首次普通技能可用所需的普攻时间。
- 仅使用普攻与闪避时的资源周转率。
- 加入看破后的资源周转率与连段延续率。
- 加入弹开后的Boss回合终止率、黄色净消耗和破韧速度。
- 普通反击与强化反击的成功率、伤害收益和灰色利用时间。
- 攻击后逃跑时蓝色自然结算对灰色的净影响。
- 主动技能路线与强化反击路线在相同初始黄色下的生命伤害、失衡伤害、风险和完成时间。
- 玩家受一次、连续两次及多次伤害后的灰色加速与恢复时间。

测试结果用于调整 `[TUNING]` 项，不得在未确认的情况下改变 `[CONFIRMED]` 结构。
