# 战斗设计维护规则

| 字段 | 内容 |
| --- | --- |
| 文档版本 | 1.0.0 |
| 适用范围 | 玩家战斗规范及其程序、动作、Boss、AI派生需求 |
| 权威设计文件 | `player-combat-spec.md` |
| 集成文件 | `integration-contracts.md` |
| 项目Skill | `.agents/skills/combat-design/SKILL.md` |

这份文档用于在设计频繁调整时避免规则遗失、重复和互相冲突。忘记维护方式时，先读取本文件，再修改战斗设计。

## 1. 单一权威来源

1. `player-combat-spec.md`是玩家战斗规则的唯一权威来源。
2. `integration-contracts.md`只负责把规则翻译成程序、动作、Boss与AI接口，不独立发明玩法。
3. Skill只负责告诉Codex如何查阅、应用和维护规范，不复制完整设计。
4. 程序文档、动作需求和Boss表可以引用规则编号，但不应复制一份长期维护的完整规则。
5. 任何派生文件与规范冲突时，以玩家规范为准，并检查冲突是派生文件过期，还是规范遗漏了已确认变更。

## 2. 修改前先判断变更类型

### 2.1 数值调整

只改变 `[TUNING]` 数值，例如帧窗口、资源量、流速或持续时间：

- 保留原规则ID。
- 更新数值和变更记录。
- 检查程序配置、动作Notify和测试基准是否受到影响。
- 不需要把数值调整描述成新的核心机制。

### 2.2 规则补充

增加原设计没有覆盖、但不改变已有规则含义的边界条件：

- 创建新的规则ID。
- 写明它依赖或补充哪些旧规则。
- 更新集成契约中受影响的事件顺序、动作字段或Boss字段。

### 2.3 规则修改

改变一个 `[CONFIRMED]` 规则的行为或设计目的：

- 修改前明确指出受影响的规则ID和冲突。
- 必须获得用户明确确认。
- 确认后先修改权威规范，再修改集成契约和派生需求。
- 在变更记录中写清旧行为、新行为和修改原因。

### 2.4 规则替换或废弃

新规则与旧规则用途不同，或旧规则仍可能被历史需求引用：

- 不复用旧规则ID表达完全不同的含义。
- 把旧规则标为 `[DEPRECATED]`，注明替代规则ID。
- 为新规则创建新ID。
- 搜索并更新所有仍引用旧ID的程序、动作、Boss和测试文档。

## 3. 标准维护流程

每次确认设计变更后执行：

1. **定位**：列出受影响的规则ID、系统和派生文件。
2. **确认**：区分这是讨论方案，还是用户已经明确接受的方案。讨论内容不能直接覆盖 `[CONFIRMED]`。
3. **修改规范**：先更新 `player-combat-spec.md`。
4. **记录历史**：更新规范中的版本、最近更新日期和变更记录。
5. **同步契约**：检查 `integration-contracts.md`中的程序事件顺序、动作字段、Boss字段和测试要求。
6. **同步实现需求**：如果已经存在程序、动画、Boss或AI文档，更新受影响引用。
7. **检查冲突**：全文搜索旧术语、废弃规则ID和已失效数值。
8. **验证链接**：确认Skill与AGENTS中的相对路径仍然有效。
9. **报告边界**：分别说明文档已更新、静态检查已完成，以及哪些内容仍需Unity、动作或灰盒运行验证。

## 4. 状态标记的使用

- `[CONFIRMED]`：结构和意图均已接受。未经明确确认不得修改。
- `[TUNING]`：结构已接受，具体数值允许根据测试调整。
- `[OPEN]`：尚未决定。程序可以预留接口，但不能自行选择永久行为。
- `[DEPRECATED]`：已被替代。必须同时注明新规则ID，等待所有引用完成迁移后再考虑移除正文。

不要因为一条规则需要灰盒测试，就把整个规则标成 `[OPEN]`。例如“反击窗口强化后扩大”可以是 `[CONFIRMED]`，具体扩大到4至8帧是 `[TUNING]`。

## 5. 规则编号

规则编号按系统域组织：

| 前缀 | 范围 |
| --- | --- |
| `VISION` / `OUTCOME` | 战斗目标、体验和胜负结果 |
| `RES-BLUE` | 蓝色资源 |
| `RES-YELLOW` | 黄色资源 |
| `RES-GREY` | 灰色资源与强化状态 |
| `LOOP` | 完整战斗循环 |
| `ATK` / `CHARGE` | 普攻与蓄力 |
| `EVADE` | 闪避、看破与Offset |
| `REPEL` | 防御与弹开 |
| `COUNTER` | 反击 |
| `SKILL` / `SKILL-LINK` | 普通技能与联动 |
| `ULT` | 奥义 |
| `HIT` | 受击、僵直与脱困 |
| `BUILD` | BD与生产接口 |
| `PROTO` | 灰盒范围和验证目标 |

新增规则在对应域末尾增加编号。不要为了整理顺序重排已有ID，否则会破坏外部引用。

## 6. 版本管理

建议使用三段版本号：

```text
主版本.规则版本.整理版本
```

- 主版本：核心战斗循环发生整体替换时增加。
- 规则版本：新增、修改或废弃一条已确认规则时增加。
- 整理版本：修正文案、链接、错别字或不改变含义的结构调整时增加。

灰盒数值调整可以增加规则版本，或在同一测试批次中集中记录。无论如何，变更记录必须能够说明数值为什么变化以及依据哪次测试。

## 7. 变更记录模板

在权威规范底部追加：

```markdown
| 版本 | 日期 | 变更 | 影响规则 |
| --- | --- | --- | --- |
| 0.2.0 | YYYY-MM-DD | 蓝色自然结算由固定延迟改为分段结算，原因是…… | RES-BLUE-05, RES-BLUE-15 |
```

复杂修改可以在表格后追加简短决策记录：

```markdown
### 决策：标题

- 日期：
- 状态：已确认 / 待测试 / 被替代
- 背景问题：
- 采用方案：
- 放弃方案及原因：
- 影响规则：
- 需要验证：
```

只记录会影响后续决策的理由，不保存冗长讨论全文。

## 8. 影响检查表

### 修改资源规则时

- 蓝色产生、结算、丢失与状态边界。
- 黄色消费、战斗内衰减与非战斗保存。
- 灰色基础流失、受伤加速、压制延续与归零退出。
- 弹开的预付顺序。
- 主动技能和道具能支付哪种资源。
- UI颜色、提示、音效和结算反馈。

### 修改动作规则时

- 前摇、有效帧、后摇。
- 闪避、防御和技能取消点。
- 反击窗口与敌人命中窗口。
- Root Motion、位移、镜头和命中停顿。
- 普通连段段数、看破Offset和回到L1的条件。
- 动画Notify与程序事件名称。

### 修改玩家应对方式时

- Boss现有攻击是否仍提供至少一种合理解法。
- 是否出现某一种应对方式对全部攻击都是最优解。
- Boss连段在看破、弹开和反击后的继续/终止规则。
- 资源风险是否仍然存在。
- 普通玩家的保底路线是否仍能进入技能消费循环。

### 修改技能或BD时

- 三个技能槽和四类技能池。
- 联动状态、消费和空窗。
- 黄色与灰色消耗。
- 是否绕过受击僵直、Boss机制或强化状态结束条件。
- 生产道具是否意外恢复灰色或形成无限技能链。

## 9. 防止文档分叉

- 不在聊天总结、任务描述或代码注释里维护另一套完整规范。
- 派生需求只写本任务必要内容，并引用规则ID和规范路径。
- 新术语必须先加入权威规范的术语章节。
- 修改机制名称时全文搜索旧名称。当前正式名称为“弹开、反击、强化反击”。
- 截图和流程图是辅助材料，文字规范仍需表达其中影响行为的规则。
- 如果程序实现与规范暂时不一致，明确标记为“实现债务”，不要反向把当前实现当成设计真相。

## 10. 忘记维护方式时如何调用

可以直接提出：

> 读取 `docs/design/combat/maintenance-rules.md`，按照维护流程更新玩家战斗设计，并列出受影响的规则ID和派生文件。

也可以调用项目 `combat-design` Skill，并说明任务属于：程序框架、动作需求、Boss/AI设计或设计修订。
